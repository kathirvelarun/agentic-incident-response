Business case & strategic value
AIR is not a replacement tool — it is a platform that compounds in value as it learns, scales horizontally across business units, and positions the organisation at the frontier of AIOps.
Direct financial impact

Engineer time saved

If MTTR drops from 47 to 19 min across ~200 incidents/month, that's 93 engineering-hours freed per month — at a blended rate of $120/hr, that is $134K/year in direct productivity.

Downtime cost avoidance

A 1-minute reduction in P1 downtime at Amex-scale is worth $100K–$500K depending on service. Targeting 5× faster P1 resolution translates to $2M–$10M/year in avoided loss.

Engineer wellbeing

Reducing 3am pages for routine incidents directly impacts retention. Replacing 60% of after-hours pages saves ~$40K/engineer in attrition risk, compounded across on-call rotations.

Audit & compliance

AI-generated, timestamped postmortems with full audit trails reduce manual compliance documentation effort by an estimated 70% — critical for DORA and PCI-DSS reporting.

Strategic & platform benefits

Enterprise-wide reuse

AIR is built as an internal platform, not a point tool. Payment teams, fraud ops, data engineering, and cloud infra all plug in to a single agent framework. One investment, multi-team ROI.

Institutional knowledge capture

Every resolved incident teaches the agent. Runbooks, incident patterns, and expert intuition become machine-readable — surviving team rotations and org restructures.

Risk & safety-first design

All agentic actions are reversible, audited, and bounded by RBAC policies. No agent can exceed its declared permission boundary. AI supervises AI at L3 autonomy.

Build vs buy advantage

External vendors (PagerDuty, ilert) charge $40–$80/user/month and own your incident data. AIR is internal IP, data stays on-prem, and the LLM layer is swappable (Anthropic, Azure OpenAI, OSS).

Alert ingestion & normalisation

Alerts arrive via webhooks (Datadog, Prometheus, CloudWatch). The AlertService normalises to a canonical AlertEvent schema, strips timestamps and IDs, and publishes to Kafka topic air.alerts.raw.

AlertController.javaAlertNormaliser.javaKafka: air.alerts.raw
2

Embedding deduplication

The DeduplicationAgent consumes air.alerts.raw, generates text embeddings via Spring AI's EmbeddingModel, performs cosine similarity search in pgvector. If similarity > 0.87, alert is grouped into existing incident.

DeduplicationAgent.javapgvector: alert_embeddingscosine_similarity()
3

Incident creation & routing

New alerts trigger IncidentService.createIncident(). The OrchestratorAgent determines severity (P1–P4) via LLM classification and routes to the correct DomainAgent based on service metadata tags.

IncidentService.javaOrchestratorAgent.javaKafka: air.incidents.created

Domain agent diagnosis (ReAct loop)

The domain agent enters a ReAct loop: Reason → Act → Observe. It calls MCP tools to pull logs, metrics, recent deployments. Spring AI's ChatClient maintains conversation state across tool calls until hypothesis confidence > 0.80.

Autonomy-level dispatch

Based on configured autonomy level (L1/L2/L3), the GuardrailEngine either posts recommendation to Slack (L1), sends Slack approval action card (L2), or executes remediation directly with rollback capability (L3).

Spring AI agent skeleton (Java)
@Service
public class DomainAgent {
  @Autowired private ChatClient chatClient;
  @Autowired private GuardrailEngine guardrails;

  public DiagnosisResult diagnose(Incident incident) {
    return chatClient.prompt()
      .system(systemPrompt)
      .user(incidentContext(incident))
      .tools(mcpTools) // MCP tool list
      .call()
      .entity(DiagnosisResult.class);
  }
  @Tool(description = "Get recent logs for a service")
  public String getLogs(String service, int minutes) {
    return datadogMcp.queryLogs(service, minutes);
  }
}
MCP servers & tool functions
Model Context Protocol bridges live operational data to AI agents. Each MCP server exposes typed tools that agents call during the ReAct loop. All calls are logged, audited, and RBAC-controlled.
MCP server registry

Datadog MCP

Exposes: query_metrics, get_logs, list_monitors, get_traces, mute_monitor. Read-mostly; mute_monitor requires L2+.

GitHub MCP

Exposes: list_recent_commits, get_diff, get_deployment, rollback_release. rollback_release requires L3 + human approval.

Jira MCP

Exposes: create_ticket, update_ticket, link_incident, get_open_bugs. Used by postmortem agent to auto-create action item tickets.

AWS / GCP MCP

Exposes: describe_instances, restart_service, scale_deployment, get_cloudwatch_logs. Write tools require L2+ and blast-radius check.

Splunk MCP

Exposes: run_query, get_alerts, get_security_events. Read-only. Used for security incident correlation alongside Datadog metrics.

ServiceNow MCP

Exposes: create_change_request, get_cmdb_item, update_incident. Used to bridge AIR incident records with ITSM for compliance reporting.

Slack MCP

Exposes: create_channel, post_message, post_action_card, get_thread, get_channel_history. Core to warroom and approval flows.

Runbook MCP (internal)

Exposes: search_runbooks (vector similarity), get_runbook_steps, execute_step, record_outcome. Powers the institutional memory loop.

Phase 1 · Weeks 1–5
Foundation, ingestion & L1 co-pilot
Core Spring Boot microservices, PostgreSQL schema, Kafka setup. Alert ingestion API, embedding deduplication (pgvector). Spring AI ChatClient integration. Slack bot with read-only agent posting RCA to warroom. Basic React dashboard.
Phase 2 · Weeks 6–10
L2 approval workflows & MCP integrations
Slack Block Kit action cards. Approval workflow state machine. GuardrailEngine with RBAC policy store. First MCP integrations: Datadog, GitHub, Jira. Domain agent framework with team-scoped runbook search. On-call scheduling assistant.
Phase 3 · Weeks 11–14
L3 autonomous remediation & postmortem AI
ConfidenceGate, BlastRadiusCalculator, circuit-breaker watchdog. Autonomous execution for pre-approved runbooks. PostmortemAgent with full timeline, RCA, Jira action items, PDF export. Analytics dashboard with MTTR trends, suggestion acceptance rate.
Phase 4 · Weeks 15–16
Hardening, multi-tenant onboarding & observability
LLM observability layer (token usage, response time, feedback loops). Performance testing at scale. Multi-team rollout tooling. Runbook AI success-rate tracking. Documentation, runbooks for AIR itself, and DR plan.
